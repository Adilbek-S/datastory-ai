# DEMO.md — защита DataStory AI за 10 минут

Тайминг: 1 мин проблема · 1 мин решение · 3 мин демо · 2 мин архитектура · 2 мин evals и A/B · 1 мин вывод.
Все числа ниже взяты из реальных прогонов (`EVALS.md`, `evaluation/results/*.json`) и из сквозных прогонов сценариев аудита; ничего не придумано.

## Подготовка (за 5 минут до защиты)

1. `streamlit run app.py`, в браузере `http://localhost:8501`. На главной карточка «Ключ OpenAI: Задан». Карточка «LangSmith» **обязана** показывать «Включена» — для этого в `.env` нужны обе строки: `LANGSMITH_TRACING=true` и ключ (см. LANGSMITH_SETUP.md; принимаются и старые имена `LANGCHAIN_TRACING_V2` / `LANGCHAIN_API_KEY`). Проверено 2026-09-28: со связкой ключа и флага трассы реально доходят до облака (`python scripts/run_sales_scenario.py`, код 0). Если карточка показывает «Нет ключа» или «Выключена» — трассировка не работает, и на защите нельзя говорить, что работает.
2. Файлы под рукой: `data/demo/sales_2026.xlsx`, `data/demo/sales_docs/sales_metrics.pdf`, `data/demo/monthly_sales_table.png`.
3. **Прогрейте сценарий A один раз до защиты** (загрузка → план → аналитика): первый вызов MCP-сервера и эмбеддингов самый медленный. Затем «Начать заново».
4. Откройте в соседней вкладке `ARCHITECTURE.md` (Mermaid-схемы) и `EVALS.md`.
5. Запасной план: 2026-09-28 исправлен главный источник нестабильности планировщика (см. ниже, было Plan Accuracy 80% → стало 96%), но полной гарантии на 100% нет. Если на живом запуске всё же появилось «назовите показатель и группировку точнее» — это честное поведение системы, нажмите «Начать заново» и повторите запрос.

## 0:00–1:00 — Проблема

- Аналитик получает выгрузку (продажи, транзакции, скриншот отчёта) и хочет быстро понять, что в ней происходит.
- Ручная работа: выбрать показатель, сгруппировать, построить график, написать вывод; названия показателей у каждой компании свои («cancellation rate», «средний чек»).
- Если отдать таблицу языковой модели «как есть», она может выдумать число или причину изменения. Нам нужны дашборд и выводы, **где каждое число посчитано кодом и проверяемо**.
- Данные приходят и картинкой (скриншот таблицы), а не только XLSX/CSV.

## 1:00–2:00 — Решение

Один экран из трёх шагов: **загрузка → план → дашборд**.

- LLM (gpt-4o-mini) предлагает **план анализа** по вопросу пользователя; код проверяет план по данным (показатель существует, колонки и значения фильтров есть).
- **Пользователь подтверждает план** (настоящий `interrupt` LangGraph) — расчёты не начнутся без него.
- Числа считает **собственный MCP-сервер** (3 инструмента), LLM только пишет текст; `verify_insights` отклоняет числа вне расчётов и причины «из воздуха».
- **RAG** (ChromaDB) подтягивает определения показателей из PDF с источником; **Skill `datastory-analysis`** — методика, которую получает модель.
- Таблицу на картинке читает **Vision**, пользователь правит и подтверждает.

## 2:00–5:00 — Demo (3 минуты)

### Сценарий A (≈ 2 мин): динамика, регионы, изменения

1. «Анализ данных» → загрузить `sales_2026.xlsx` (288 строк, 7 колонок, период 2026-01 — 2026-06) и `sales_metrics.pdf` (индексируется: «7 фрагментов»).
2. Запрос: **«Покажи динамику выручки по месяцам, сравни регионы и найди основные изменения»** → «Составить план анализа».
3. Показать **план** (≈ 7 с в прогоне аудита): два шага — «Динамика выручки по месяцам» (Month, Region; линейный) и «Сравнение выручки по регионам» (столбчатый); у обоих: «Определение показателя найдено в документации: sales_metrics.pdf, стр. 1, раздел «2. Выручка (Revenue)»». Сказать: **здесь граф стоит на паузе** — это human-in-the-loop, ничего ещё не посчитано.
4. «Построить аналитику» (≈ 3–4 с в прогоне аудита). На дашборде показать: KPI «Revenue: итог 1,35 млрд KZT»; блок «Расчёты выполнил MCP-сервер» и «Методика: Skill `datastory-analysis`… правила V1–V6, A1–A7»; вывод «наибольший рост в Алматы 17,37 млн KZT, 22,0%» (сверено с Python: +17 367 165, +22,0%); значок калькулятора и «На основе: MCP calculate_metrics…»; «Причина изменения по данным не установлена».
5. Чат: «Какие изменения заслуживают внимания?» → ответ называет падение общей выручки в апреле на 18,43 млн и рост к маю на 36,05 млн (обе цифры совпадают с расчётом по данным). «Скачать отчёт» — Markdown.

### Сценарий C (≈ 1 мин): таблица на изображении

1. «Начать заново» → загрузить `monthly_sales_table.png`. Vision: «Таблица распознана моделью gpt-4o-mini: 6 строк, 3 колонок» (во всех 9 сохранённых прогонах аудита все 18 значений совпали с эталоном, ≈ 1,5 с). Показать редактируемую таблицу и «Подтвердить распознанную таблицу».
2. Запрос **«Покажи динамику показателя по месяцам»**. Запрос намеренно расплывчатый (в таблице Orders и Revenue_KZT): система строит «Динамика выручки по месяцам» и просит подтвердить формулу (нет определения в документации) — хороший повод показать честную ветку «нет документации, нужно ваше подтверждение», а не молчаливую догадку.

### Сценарий B (запасной, 30 с): доля отмен

`sales_2026.xlsx`, запрос **«Покажи cancellation rate по месяцам»** → один шаг `Cancelled Orders / Orders`, 4,41% → 4,33%, максимум 4,51% в марте (совпадает с Python). Без PDF карточка просит подтвердить формулу — показывает ветку «нет определения в документации».

## 5:00–7:00 — Архитектура (2 минуты)

Открыть схему из `ARCHITECTURE.md` («Архитектурная схема») и sequence-диаграмму.

- **Streamlit** → `AnalysisRunner` (свой `thread_id` на сессию) → **LangGraph**: `analyze_intent → retrieve_context → build_analysis_plan → validate_analysis_plan → human_approval → execute_analytics → generate_insights → verify_insights → prepare_dashboard`.
- **Условные переходы**: план пуст → конец; `human_approval` → approve / revise (назад к плану) / cancel / повторный вопрос; `verify_insights` → повторная генерация при нарушениях.
- **MCP-сервер** (FastMCP, stdio, дочерний процесс): `profile_dataset`, `calculate_metrics`, `create_chart_spec`; ни `eval`, ни SQL, ни LLM внутри.
- **RAG**: ChromaDB + `text-embedding-3-small`; фрагменты с источником (файл, страница, раздел).
- **Skill**: `SKILL.md` с правилами V1–V6 и A1–A7; текст правил не дублируется в коде, а код проверяет соблюдение.
- **Vision**: изображение → `TableExtraction` → редактируемая таблица → общий профайлер.
- **LangSmith**: span-ы для графа, LLM, RAG, MCP, Vision — включаются ключом. **Честно:** в этой сборке ключа LangSmith нет, доставка трасс в облако не проверялась; проверены создание span-ов в тестах и честный статус «выключена».
- Trade-off для слайда: числа считает код — выводы проверяемы, но набор расчётов ограничен; LLM-планировщик гибкий, но недетерминированный (см. следующий блок).

## 7:00–9:00 — Evals и A/B (2 минуты)

Открыть `EVALS.md`.

**Golden dataset**: 30 синтетических случаев, 6 групп по 5 (интерпретация показателя, динамика, сравнение категорий, фильтры, терминология из базы знаний, недопустимые/неоднозначные); эталонные числа посчитаны на чистом Python.

**Результаты полного прогона (после фикса планировщика, 2026-09-28):** Retrieval Hit@3 — 100% (26/26); Numeric Accuracy — 100% (25/25) (MCP считает точно); Analysis Plan Accuracy — **96% (24/25)**; недопустимые запросы отклонены 3 из 4. До фикса на этом же наборе колебалось 96% → 100% → 80% — модель иногда заполняла в `PlanDraft` поле `charts` вместо `steps`, и разумный ответ считался пустым; схема и retry-подсказка это теперь явно запрещают, на пяти ранее падавших случаях — 35/35 повторов подряд. Единственный оставшийся промах — `iv-03` («покажи прибыль по регионам»): отдельная, не исправленная проблема — показатель иногда подменяется вместо отклонения.

**A/B (RAG в промпте планировщика: A — без, B — Top-5), 30 случаев × 3 повтора:** Plan Accuracy A 89,3% (67/75) и B 90,7% (68/75); разница +1,3 п.п., 95% ДИ [−6,7; +9,3] — **не подтверждено**. RAG-dependent случаи: 80% и 80%. Retrieval Hit@3 для B — 100% (78/78): поиск находит нужный документ, но точность плана от контекста не растёт. Вывод «RAG лучше» система не формирует, пока ДИ не выше нуля. **Оговорка:** этот прогон был до фикса планировщика — абсолютные проценты сейчас были бы выше в обеих конфигурациях, но сама разница между A и B вряд ли изменится (баг не зависел от наличия RAG).

**Гиперпараметры (temperature 0 против 0,4, 10 случаев × 5 повторов, тоже до фикса планировщика):** точность 80,0% и 87,5% (не различимы); стабильность структуры 94% и 86%; токены 7 484 и 6 643 (0,4 экономнее). Выбрана **temperature 0, max output tokens 1024** по заранее заданному правилу (стабильность); выбор слабый, первый запуск дал обратный вариант — оба сохранены в EVALS.md.

## 9:00–10:00 — Вывод

- Реально работает сквозной путь: XLSX/CSV/PNG → план с подтверждением → расчёты через MCP → проверенные выводы → чат → отчёт; определения из PDF находятся и цитируются.
- Числа не выдумываются: MCP совпал с эталоном Python во всех 25 случаях evals; в сценарии B все 6 значений совпали с Python, в сценарии A — 4 из 4 регионов и 14 проверенных точек «месяц × регион».
- Главный источник нестабильности планировщика найден и исправлен 2026-09-28 (Plan Accuracy 80% → 96%); осталось: `iv-03` не отклоняется, и выводы не всегда называют самое крупное изменение.
- Следующий шаг: повторить A/B и выбор гиперпараметров на исправленном планировщике (те результаты в EVALS.md получены до фикса).

## Вопросы, к которым стоит быть готовым

| Вопрос | Честный ответ |
|---|---|
| Трассы LangSmith реально есть? | Да — проверено `python scripts/run_sales_scenario.py`: 3 корневые трассы (`datastory.analysis.plan/.approve`, `datastory.chat.ask`) с span-ами `llm.*`, `mcp.*`, `rag.*` реально дошли до облака LangSmith. Нужны обе переменные в `.env`: `LANGSMITH_TRACING=true` и ключ. |
| Почему выбран gpt-4o-mini, а не Claude/Gemini? | Сравнительных evals между провайдерами не проводилось — решение по трём конкретным причинам: структурные ответы через `with_structured_output`, одна модель для текста и Vision, цена (см. ARCHITECTURE.md, «Выбор LLM»). Один вызов построения плана — измеренно ≈ $0.001 (по официальной цене OpenAI, могла измениться). |
| Что если LLM недоступна? | Реальный fallback — детерминированные правила (каталог анализов), не другая модель; пользователь видит предупреждение. Проверено тестами и `--no-llm` в evals. |
| Почему Plan Accuracy менялась от прогона к прогону (96→100→80%)? | Модель иногда клала шаги в поле `charts` схемы вместо `steps`; проверка «пустой ответ» смотрела только на `steps`. Исправлено 2026-09-28: схема и retry явно запрещают `charts` здесь. Стало 96% (24/25), на пяти ранее падавших случаях — 35/35 повторов. A/B и гиперпараметры в EVALS.md получены до этой правки. |
| RAG нужен? | A/B не подтвердил прирост точности плана. RAG нужен для определений и цитат с источниками (в сценарии A определение Revenue найдено в PDF) — это не измерено метрикой плана. |
| Golden dataset независимый? | Нет: синтетический, промпты дорабатывались на близких запросах — значения завышены. |
| Почему не нашли падение Astana в апреле (−36%)? | Вывод по графику с четырьмя сериями назвал только самый большой рост; в чате падение называется для общей выручки. Известное ограничение. |
| Что с «прибылью»/Return Rate? | Часть прогонов заменяет неизвестный показатель близким (в списке «Не выполнено» он при этом перечислен); EBITDA и прогноз отклоняются. |
